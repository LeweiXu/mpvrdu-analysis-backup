# How this report is put together

`results/tables/` holds three peer reports. Each has the same three kinds of file:
the per-table CSVs, `all_tables.md` (every table in full, with captions, confidence
intervals and per-cell n), and `summarised_tables.md` (the same tables condensed).

| directory | what it is |
|---|---|
| `mmlongbench/` | MMLongBench-Doc: the main experiment, 847 answerable questions |
| `longdocurl/` | LongDocURL: the second corpus, same pipeline and builders |
| `unified/` | only the quantities that mean the same thing on both |

This file records the calls that were judgement rather than mechanism. The durable
copy of these decisions is `docs/DECISIONS.md`; this one is regenerated by
`ops.build` so it cannot drift from the layout it describes.

## 1. Why MMLongBench moved into a subdirectory

It used to sit at the top level with LongDocURL nested inside it, which read as if
one report owned the directory and the other was a guest. Three peers is the honest
shape now that there are three. Everything that consumed the old flat paths (the
figure scripts under `ops/scripts/`, `visualize_app/build_data.py`,
`check_worked_examples.py`) was repointed at `mmlongbench/`.

## 2. What `summarised_tables.md` is

The same tables as `all_tables.md`, in the same format, condensed so the report can
be read rather than looked things up in. Four things happen to every table, and each
table's note records which of them applied to it:

- **Verbose columns go.** A transition table keeps `wrong→right` and `right→wrong`
  and drops `right→right` and `wrong→wrong`, which are their complement and carry no
  extra finding. Bootstrap `CI low`/`CI high` and bookkeeping columns go the same
  way.
- **Confidence intervals come out of the cells.** They are the single biggest source
  of width, and the full table is one file away. The point estimate and n stay.
- **The shared baseline is stated once**, in the preamble, instead of under every
  table. A caption then carries only what is specific to that table, which is
  usually just the swept axis.
- **Only the genuinely unreadable cross-tabs lose rows.** The bar is 60 rows,
  deliberately high: the per-group breakdown *is* the finding in most tables, so a
  fidelity table keeps its doc_types beside the pooled row. In this report only the
  two selection-transition tables (140 and 210 rows) are cut to their own pooled
  rows. A few tables with no pooled row instead keep the slice the report quotes:
  retrieval at k = 1, 5, 10; the OOM frontier where the rate is non-zero; selection
  at the ranker the figures use.

That takes the MMLongBench report from 259K to 127K without dropping a table.

`summarised_tables.md` is generated. To change what it says, change
`reporting/summarise.py`, not the file.

## 3. Where the two datasets' reports diverge

Most LongDocURL tables are *rebuilds*: the same builder, the same layout, run over
LongDocURL rows. That is right for anything both corpora annotate the same way
(evidence source, single/multi hop, the rungs themselves). It is wrong for the
labels only one of them has, and LongDocURL's are the reason for running it.

**LongDocURL has no document-domain labels.** MMLongBench splits its headline on
`doc_type` (Academic paper, Brochure, Financial report); LongDocURL has nothing
equivalent, and the loader puts its `task_tag` in that field. The rebuilt tables
therefore printed a `doc_type` column holding something that is not a document
type. Those tables now name it **`task_tag`** and print it in its own order
(Understanding, Locating, Reasoning) rather than alphabetically.

**What it has instead**, and now gets its own tables for:

| grouping | classes | why it is worth a table |
|---|---|---|
| `question_type` | 9 | the finest question annotation either corpus carries, nested inside `task_tag` |
| `answer_format` | 5 | String / List / Integer / Float / None, which MMLongBench does not annotate |

`question_type` prints grouped by the task tag each type belongs to rather than
alphabetically, so the three families stay legible as blocks. Both are also crossed
with hop, because hop is the axis both corpora share and question type is the axis
only one has: `ldu_integration_question_type` is the pairing the second dataset
exists to produce.

**How the sharing works.** The grouping is the parameter and the builder is shared
(`reporting/tables/_grouping.py`). A `Grouping` says what the column is called, which
buckets a row falls into (possibly several, for a multi-label axis like evidence
source), and what order they print in. `grouped_ladder` takes one and is the base
under every ladder table in both reports; `integration.build` takes one too. So
MMLongBench's doc_type headline and LongDocURL's question-type ladder are the same
code with a different grouping, which is what keeps the layouts honest against each
other. The MMLongBench report is byte-identical across this change.

**Neither label reaches the result rows.** A row records how a cell was run, not how
its question was annotated, so `question_type` and `answer_format` are joined from
the corpus by `question_id`, cached per dataset. The join is verified two ways: it
reproduces the task-tag table built from the row field exactly, and it covers all
11,585 prediction rows with nothing unmatched.

**Not in the unified report.** `question_type` and `answer_format` have no
MMLongBench counterpart at all, so there is nothing to put beside them; see the
exclusions in section 4.

## 4. The unified report

### Evidence sources had to be reconciled

The two corpora label evidence differently. LongDocURL has four categories where
MMLongBench has five, and the join is not one-to-one:

| unified | MMLongBench-Doc | LongDocURL |
|---|---|---|
| Text | `Pure-text (Plain-text)` | `Text` |
| Table | `Table` | `Table` |
| Layout | `Generalized-text (Layout)` | `Layout` |
| Figure | `Figure` **and** `Chart` | `Figure` |
| *(excluded)* | `(none)` | `Others` |

Two calls here. **MMLongBench's `Chart` folds into `Figure`**, because LongDocURL
draws no chart/figure line and the split cannot be recovered on its side; a chart is
a figure, so the merge loses resolution rather than inventing it. **`(none)` and
`Others` are dropped rather than paired**: MMLongBench's marks a question with no
labelled source at all, LongDocURL's is a genuine 8-question residual category, and
equating them would manufacture a correspondence that does not exist.

### What is in `unified/`, and why it survives the move

- `unified_ladder` — the representation ladder. Both corpora run the same five rungs
  on oracle pages with the same reasoner, so the rung means one thing.
- `unified_ladder_source` — the ladder by reconciled evidence source.
- `unified_integration` — the single/multi-page gap. The most directly comparable
  quantity in the report: `hop` comes from the question's gold evidence-page count,
  which both corpora annotate the same way.
- `unified_retrieval` — page recall by retriever at shared depths.

### Every unified table carries a third row: MMLongBench-Doc (digital)

Scan status is the one corpus difference big enough to change the reading, so it is
controlled rather than caveated. MMLongBench-Doc is **29 of 135 documents scanned**
(190 of 847 answerable questions); LongDocURL is **2 of 396** (5 of 2,317). A
scanned page has no embedded text layer, so **24.5% of MMLongBench questions sit on
an evidence page whose `T` text is empty**, against 0.8% on LongDocURL. The
unfiltered MMLongBench row therefore prices OCR failure and the reasoning task
together, while the LongDocURL row beside it prices only the second.

`MMLongBench-Doc (digital)` is the same pool, same cells, restricted to documents
PyMuPDF classes as born-digital. It is a **subset of the row above it**, not a
separate run, and it is the row to read against LongDocURL.

The filter reads `annotations/auto_scan.csv` (derived from the PDFs, covers every
document in both corpora), **not** the row's own `scan_label`. That field is stamped
at generation time from `annotations/doc_labels.csv`, so a tag generated before a
document was labelled carries a blank one permanently: 4,152 complete-pool rows over
28 documents are blank for exactly that reason. Where a row does carry a label the
two agree.

**It matters most where the ladder is concerned, and not at all for integration.**
`T` goes 31.9 -> 39.9 once scans are dropped and `T -> best` halves, 20.7 -> 10.2,
against LongDocURL's 8.1 — so most of the apparent "vision buys twice as much on
MMLongBench" is the scanned documents flooring the text rung, not a corpus-level
difference in how much images help. The integration gap barely moves (-25.0 ->
-26.8 at TLV against LongDocURL's -5.4), so that finding is robust to the confound.
The retrieval table shows the mechanism directly: the text retrievers gain
substantially on digital-only (bm25 R@1 0.222 -> 0.279) while the vision retrievers
do not move at all (colqwen3 0.541 -> 0.542), which is what a text-layer confound
should look like.

### What was deliberately left out

- **Document type / task category.** MMLongBench's `doc_type` is a document genre
  (Academic paper, Brochure, Financial report); LongDocURL's is a task category
  (Locating, Reasoning, Understanding). They occupy the same column in each report
  and mean entirely different things, so no join exists.
- **The parser, resolution, quantization and reasoner sweeps.** Run on MMLongBench
  only; there is no LongDocURL side to put beside them.
- **Faithfulness, hallucination and abstention.** These need an unanswerable pool,
  which LongDocURL does not have.
- **A scanned-vs-digital split on LongDocURL.** It has 2 scanned documents and 5
  questions on them, so the split does not replicate; the MMLongBench-side control
  is the `(digital)` row above instead.
- **The distractor robustness sweep.** Both corpora ran one, but not comparably:
  MMLongBench covers four rungs and two rankers to k=6, LongDocURL one rung and one
  ranker to k=5, and its shards are still partly judged. Putting them side by side
  would compare two different experiments.
- **OOM and VRAM telemetry.** A property of the card and the page count, not of the
  dataset's difficulty, and the two pools differ in page count by roughly 2x.

### The caveat that applies to every unified table

**Levels are not comparable across datasets; the response to an intervention is.**
LongDocURL documents run 51-149 pages (mean 89) against MMLongBench's 47.5, its
questions carry more gold pages, and 14.6% of them are multiple-choice or yes/no
against MMLongBench's 1.4%, which puts a floor under its accuracy that MMLongBench
has no equivalent of.
Its accuracies are higher throughout, and that is a property of the corpus, not
evidence about a method. Every unified table therefore carries a per-dataset delta
(`T -> best`, `M-S`) alongside the levels, and that delta is what the two rows can
be read against each other on.

## 5. Standing caveats in the data

- **LongDocURL is still filling in.** Generation and judging are both in flight, so
  its tables move between builds. Check each table's n before quoting it.
- **OOM attrition is nested, not random.** Questions that fail at a high page count
  are a superset of those that fail lower down, so a thin cell is the surviving
  lightest questions. Where this mattered enough to mislead, the report carries a
  matched-pool table beside the per-condition one (`selection_distractor_matched`).
- **One reconciliation check still fails by design** on MMLongBench, which withholds
  `faithfulness_pools`. It is explained in that report's Reconciliation section.
